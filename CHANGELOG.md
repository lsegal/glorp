# Changelog

## Unreleased

- Decode an agent's output, capture its session ID, and recognise its "that session is gone" message from the agent's own definition, so a CLI that streams something other than Codex's plain text or Claude's event envelope is read by describing it rather than by editing `runOnce`. Reading an agent was the last part of talking to one that was still hardcoded: stdout was wrapped in Claude's `stream-json` decoder when the agent was named `claude`, scraped for a session ID with a Codex-shaped regular expression when it was named `codex`, and scanned for one global list of missing-session phrases whichever agent produced it. A definition's `output` block now selects the decoder -- `plain` for output shown as it is written, `claude-stream-json` for the existing decoder, and a new `jsonl` decoder for any line-delimited JSON stream, configured with field paths rather than Go code: which key holds the event type, which holds the text, which hold a tool call's name and its input, and which event types to skip, with a `[]` suffix stepping into an array so `message.content[].text` reads every content block. The generic decoder renders tool calls as the same `Running: ...` progress lines Claude's does, pairs a call's name with its own input rather than the next block's, passes a line that is not JSON through untouched -- banners, warnings, and stack traces are exactly what someone debugging a failed run came for -- and renders nothing at all for an event shape the definition does not describe, so an unknown or malformed event never drops the stream. Session-ID capture reads the pattern from the definition alone, with Codex's expression now living only in `codex.json`, and `missingSession` is a per-agent list defaulting to today's shared phrases, so an agent whose wording is distinctive adds it without loosening detection for every other agent. `GLORP_CHECKOUT_DIRECTORY=` parsing stays agent-independent, since that marker is glorp's own protocol rather than any agent's. Codex and Claude render byte-identical output through the definitions they already ship, pinned by their unchanged decoder tests, and the contract harness gains an agent that exists only as JSON -- its own event stream, its own session regex, its own missing-session phrase -- proving the whole path without a line of Go describing it.

- Dispatch issues to [Cline](https://cline.bot) with `--agent cline`, which is now one of the agent definitions glorp ships rather than something you have to declare in `.glorp.config.json` yourself. Cline's CLI is a standalone binary that needs no editor host, and its default mode is exactly what a dispatch wants -- act mode with tool auto-approval, taking the prompt as a positional argument and never opening the TUI unless `-i` asks for it -- so the definition renders `--auto-approve true`, then `--model` and `--thinking` when the `--agent cline/model:level` spec names them, then the prompt. `--thinking` takes `none`, `low`, `medium`, `high`, or `xhigh`, and the definition's allow-list is that set, so a level Cline would reject is answered by glorp with the list instead of by Cline with a usage error one dispatch later; a model is passed through untouched, since Cline's ids are provider-scoped (`anthropic/claude-fable-5.1`) and its catalog is live. What Cline has no headless equivalent of is resume: `cline --id <session>` switches the CLI into its interactive TUI even with a prompt passed positionally, and then refuses to run at all without a terminal, so there is no session for glorp to assign or to read back from the output. The definition declares that with `"session": {"assign": "none"}` and gives a resume template that simply restarts the work with the recovery prompt, so a run glorp picks back up continues from the pull request and the branch rather than from Cline's own conversation -- which is what the recovery prompt already asks for -- instead of failing the job. Its output is decoded as plain text; Cline does have a `--json` event stream, but it is its own envelope rather than the one glorp's streaming decoder reads, so that is left to the pluggable decoding work. Quota reporting has no Cline equivalent to read. The definition names `cline` as its skills.sh target, which is the id skills.sh already knows the CLI by, so the registry-driven installers install the `gh-fix` and `gh-discuss` skills for it alongside Codex and Claude Code and a dispatched run finds the slash command it is sent.

- Install the `gh-fix` and `gh-discuss` skills for every agent glorp knows about, derived from the agent registry instead of a flag list edited by hand. Both installers called `npx skills add ... --agent codex --agent claude-code`, so an agent definition added to the registry shipped with glorp able to dispatch to it and with neither of its skills installed, until someone remembered to edit two scripts in a third language. An agent definition now carries a `"skills"` block naming its skills.sh target id -- a dedicated one such as `codex` or `claude-code`, or `universal` for a CLI skills.sh has no dedicated id for -- and a new `glorp agents` command lists the registered agents, or with `-skills` the deduplicated target ids they install skills for. `install.sh` and `install.ps1` ask the binary they have just installed for that list and build their `--agent` flags from it, so adding a built-in definition needs no installer change; a binary that cannot answer stops the install after glorp itself is in place, naming the `skills add` command to run by hand, rather than quietly installing skills for the wrong set of agents. Agents declared in `.glorp.config.json` may name a target too, and install their own skills with the same command, which the README now spells out along with the new subcommand.
- Cache the Go module and build caches in every workflow that sets Go up, so a run stops rebuilding the standard library and every dependency before it reaches the first test. `actions/setup-go` does cache both directories, but under a single key derived from `go.sum` with no restore-keys, which fails in both directions: a dependency bump misses that key outright and builds completely cold, and while `go.sum` is unchanged the key keeps hitting exactly, so the entry is never re-saved and the compiled objects for glorp's own packages stay frozen at whatever the tree looked like the day a dependency last moved -- which for the Linux CI job means recompiling the repository four times over, for `go test -race`, `go vet`, `GOOS=darwin go vet`, and the production-tagged pair. The built-in cache is now off and a shared composite action does the work instead: it asks the toolchain for `GOMODCACHE` and `GOCACHE` rather than hardcoding paths that differ per platform, and keys on the Go sources as well as `go.sum`, falling back through any cache for the same dependencies to any cache for the same job, so an ordinary source edit starts warm rather than from nothing. Both CI jobs, the release job, and the finalize-release job use it; the last keeps its own cache namespace because it cross-compiles six `GOOS`/`GOARCH` pairs and shares almost no compiled object with a native run, while the release job deliberately shares CI's, since it compiles the same packages the same way and runs rarely enough to be cold otherwise. The Pages workflow is untouched, as it builds only the Hugo site and uses no Go.

## v1.2.34 - 2026-09-03

- Stand down for a claim another instance posted minutes ago on the first reap after startup, instead of asking past it and dispatching work that is actively running. The previous entry closed this hole on the uncontested pickup path; the contested path kept it on its first pass, and a freshly restarted instance is exactly where it bites, because with no local work records everything it sees reads as a candidate. That first reap is deliberately aggressive -- it runs before the periodic reap timer, so work nobody holds is picked up at startup rather than waiting -- but being aggressive was implemented as skipping the claim read entirely and going straight to the ownership handshake, and the handshake only reads answers posted after its own ask. An instance that announced `Starting work on this issue` five minutes earlier does not re-announce during the grace window, so nothing answered, the ask went unchallenged, and both instances ran an agent on the same ticket. Both reaps now read the ticket's standing claims first and stand down for a foreign claim newer than the staleness window, leaving the issue marked as seen so a later poll renegotiates it once that claim goes stale. What the first reap still skips is only the guards that exist to stop a periodic pass re-asking -- this instance's own standing claim and a handshake it already settled -- so a stale foreign claim and a ticket with no claim at all are reaped immediately on startup exactly as before, and a comment read that fails there negotiates rather than stranding abandoned work until the next reap, since the handshake is itself an ask a live instance can answer.
- Read the claims already standing on a ticket before picking it up as uncontested, so two instances stop working the same issue at once. Whether an issue was contested was decided from this instance's own work records and the project board alone: an issue nobody here had a record of, whose card was not at `In Progress`, read as untouched work and was dispatched immediately, with its `Starting work on this issue` claim posted afterwards. The handoff comments other instances had already posted on the ticket were never part of that decision -- they were read only on the contested path, by the reap -- so an issue one instance announced it was starting was picked up by the next instance to poll it minutes later, and both ran an agent on it and opened their own pull request, which is what happened to issue #487. A first-time pickup now reads the same claims the reap does, on the pull request continuing the work when one is open, and stands down for a claim another instance posted within the staleness window instead of dispatching; the issue stays marked as seen, so the next poll routes it through the ownership handshake, where a claim that goes stale is still reaped as abandoned. Work this instance holds the newest claim on, work whose newest foreign claim has already expired, a resumed session, and an issue whose newest comment is an `@/glorp:ID` mention addressed to this instance are all dispatched exactly as before, the check costs one comment read per issue actually about to be dispatched, and a comment read that fails picks the issue up rather than stalling the watch.
- Describe the agent CLIs glorp dispatches to as JSON definitions instead of as `codex`/`claude` branches spread through the code, so supporting another CLI is a config file rather than a build. Every place that had to know how to talk to an agent carried its own arm of the same two-way `if`: `parseAgentSpec` accepted no name but those two, `commandArgsForSession` built two hardcoded argv shapes for a fresh run and a resume, `browserVisionArgs` built a third pair for the one-shot screenshot read, `CommandRunner.binary` mapped the name to `--codex-binary` or `--claude-binary`, and `runOnce` hardcoded Claude's `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, Codex's stdout session-ID capture, and Claude's stream-json decoder -- six sites to edit per agent, each an opportunity to get one of the six subtly wrong. An agent is now a definition: the executable, the argv template for a fresh run, a resume, and a vision call, the environment its child process gets, whether glorp assigns its session ID or reads one back from a line it prints and whether that ID survives a failed resume, the models and levels `--agent` accepts, and how its output is decoded. `codex` and `claude` are two such definitions, embedded as JSON and loaded at startup, and the arguments they render are byte-identical to what the branches produced -- pinned by a table covering every mode, flag, and model and level combination, on top of the existing tests, which pass unchanged. `--agent` validates against the registry rather than a hardcoded pair, so an unknown name is answered with the agents that do exist instead of "agent must be codex or claude", and a level or model outside an agent's own list is answered with that agent's list.
- Read agent definitions from `.glorp.config.json`, a new file `--config` points elsewhere, so a CLI glorp does not ship can be declared without waiting for a release. The file is read-only to glorp and deliberately not `.glorp.json`: that one is the work state the daemon rewrites as issues are handled, and a hand-edited definition living there would be destroyed by the next save, so definitions found in the state file and work-state records found in the config file are both reported pointing at the other file rather than half-working. Its shape is a top-level object with an `agents` section -- an array of definitions or an object keyed by name -- leaving room for later sections instead of being a bare array. A definition whose name matches a built-in overrides it field by field, keeping everything it does not mention, with a field given as `null` dropping what it inherited; an unknown name registers a new agent, which `--agent` then accepts and dispatches through the executable its own definition names. A missing file is not an error and a default run behaves exactly as before, but malformed JSON, an unknown field, or an invalid value stops the run naming the file, the agent, and the field, because a definition dropped quietly is indistinguishable, at the `--agent` prompt, from a typo in the name.
- Prove those definitions in CI against a fake agent CLI, since the real ones cannot be run there. The vendor CLIs are not installed on the runners and most need credentials, so a definition's claims about argv, environment, session capture, and output decoding would otherwise be untested until someone ran it by hand. A small program built by the test now stands in for them: it records the argv, working directory, and environment of every invocation, and on demand announces a session ID, prints a checkout-directory marker, emits a configured output stream, reports a session it no longer holds, or exits non-zero. A reusable contract harness points a definition at it and drives a fresh dispatch, a resume, and a resume whose session is gone through the real `CommandRunner`, checking the argv of each, the session ID glorp ends up holding, the decoded output, and that a dead session restarts the work rather than failing it -- with the dead ID dropped for an agent that assigns its own and kept for one glorp assigns. `codex`, `claude`, and an agent that exists only in a config file each have a contract test on it, and the agents added later get theirs by filling in the same struct. It needs no network, runs on Windows as well as Unix, and is clean under `go test -race`.
- Record that no lever makes a headless Claude run viewable from a phone, instead of leaving the question open for a third investigation. `--remote-control` was turned off by default once `remoteControlAtStartup` proved inert under `-p`, but no replacement was looked for, so the original goal — looking in on a running agent from the Claude mobile app or claude.ai/code — stayed unmet and undocumented. Each remaining candidate was measured against Claude Code 2.1.248 with a real headless run rather than read off documentation, and all of them fail. `autoUploadSessions`, the hoped-for view-only mirror, is not a Claude Code setting at all: it is absent from the settings reference, and a `-p` run with every debug category enabled makes no upload or session-share request of any kind, so there is nothing to turn on. `claude remote-control`, the separate server mode, hosts only the sessions it creates itself, so glorp cannot hand it a `claude -p` child it already started: its `--session-id` takes a server-side code session rather than a local session UUID and rejects one as `invalid session ID: must be a cse_… or session_… tagged ID`, it refuses to start until the workspace trust dialog has been accepted interactively — which a `-p` run never triggers, because print mode skips that dialog — and it then asks `Enable Remote Control? (y/n)` on the terminal. The remaining answer is a Claude Code change that reads the setting on the print-mode startup path, filed upstream as [anthropics/claude-code#91906](https://github.com/anthropics/claude-code/issues/91906) and recorded next to the arguments glorp still passes so it is not re-derived. `--remote-control` keeps its behaviour and its default, and now says at startup, in the terminal and the dashboard log, that it currently reaches nobody and where that is tracked, rather than being an opt-in that quietly does nothing.
- Stop turning Remote Control on for Claude runs by default, because Claude does not act on it when it is launched headlessly. The default was shipped on the assumption that `--settings {"remoteControlAtStartup":true}` starts the same Remote Control bridge outside the interactive startup path, and the runtime effect was never exercised. It does not: measured against Claude Code 2.1.248, a `claude -p` run started with exactly the arguments glorp passes records no bridge session, keeps the session name Claude derives from the working directory instead of the `glorp owner/repo#N` name given to `--rc`, and is discoverable only as a session local to the machine, so nothing ever appears on a phone or at claude.ai/code. The same `--settings` payload does change the model in the same run, so the setting arrives and is simply not read under `-p`, matching what `claude --help` says of the flag it mirrors: `--remote-control` starts "an interactive session with Remote Control enabled". `--remote-control` is now off by default and kept as an opt-in that passes the same arguments as before, so a Claude release that honours the setting in print mode needs no change here, and glorp no longer advertises a capability its runs do not get.
- Say once, at startup, that `--remote-control` passes nothing to a Codex run, instead of accepting the flag on a Codex watch and silently doing nothing with it. The previous entry kept the flag as a Claude opt-in; on the Codex side there was never anything to pass, so `--agent codex --remote-control` took the flag, changed no argument, and gave no hint why the run stayed off the phone. A watch that has Remote Control on and a Codex agent configured now prints, and logs to the dashboard, that remote control is not passed to Codex runs and that they stay viewable in glorp's own dashboard; a Claude-only watch and a watch left at the default print nothing, and Codex runs themselves are dispatched exactly as before. The `codex remote-control` daemon was investigated as the mechanism that could have changed this and rejected: it is the app-server hosting the threads it starts itself, so there is nothing to hand it a `codex exec` process glorp has already started, and being hosted by it at all would mean driving Codex over the app-server protocol instead of `codex exec`. Its `start`, `stop`, and `pair` commands also refuse to run anywhere but Unix, pairing a device to it is a manual step glorp cannot complete, and starting or stopping a machine-wide daemon underneath a user who paired one themselves would disrupt their own sessions. Codex's own `remote_control` feature flag is marked removed and `codex exec` exposes no equivalent argument, so Codex runs stay local until Codex ships a per-run option. The `--remote-control` README row records all of this instead of stating only that Codex is unaffected.

## v1.2.33 - 2026-09-03

- Run ngrok through `npx` when it is not installed, so the default webhook mode no longer requires a separate ngrok install. glorp shelled out to an `ngrok` executable and failed outright when `PATH` had none, which made a manual ngrok install a prerequisite even though Node.js and `npx` already were one for the installer. `glorp watch` now looks for the configured executable first and, finding none, starts the agent as `npx --yes ngrok` instead, printing why it did so. An installed ngrok is still preferred and runs exactly as before, and a `--ngrok-binary` set to anything other than the default is still required to exist rather than being quietly replaced by a download. The first npx run has to fetch the package and the agent before ngrok says anything, so the startup budget for that path is two minutes rather than ten seconds, and npm's own deprecation and progress notices are kept out of glorp's UI while a genuine `npm error` is still reported as the reason no tunnel came up.
- Make agent runs viewable from the Claude mobile app and claude.ai/code by default, so a long run can be followed, and picked up, away from the machine it started on. glorp launches Claude headlessly with `-p`, and a headless run previously existed only inside glorp's own dashboard: there was no way to look in on it from a phone. Passing Claude's `--remote-control` flag does not help on its own, because Claude reads that flag only on its interactive startup path and silently ignores it under `-p`. Claude runs now receive `--settings {"remoteControlAtStartup":true}` instead, which starts the same Remote Control bridge without going through the interactive path and is layered on top of your own settings rather than replacing them, together with `--rc "glorp owner/repo#N"` so several concurrent runs are told apart by the issue each one is working on instead of all appearing under the same host name; a resumed run reconnects under that same name rather than adding a second entry. The new `--remote-control` flag is on by default and turns the behaviour off with `--remote-control=false`. Codex runs are unchanged, because Codex exposes Remote Control only through its separate `codex remote-control` daemon and has no equivalent argument for `codex exec`.

## v1.2.32 - 2026-09-03

- Stop a `gh-fix` run short of merging when the issue itself withholds that authorization, instead of merging anyway. An issue whose body, comments, or labels said the fix should not be merged -- a `donotmerge` or `hold` label, or a comment asking that it be left for someone to look at first -- was read for its request and nothing else, so the skill drove the pull request to green CI and merged it exactly as it would any other ticket, and the only way to keep a change out of `main` was to not dispatch the issue at all. Validation now reads the issue for a merge hold before any code is written, matching a hold label case-insensitively and ignoring separators (`donotmerge`, `do-not-merge`, `no-merge`, `hold`, `needs-review`) as well as wording anywhere in the thread that asks for the merge to stop, with the most recent comment winning so a hold can be imposed or lifted mid-run. A held run is otherwise unchanged -- it implements, tests, writes the changelog note, pushes, marks the pull request ready for review, and drives CI to completion -- and then leaves the pull request open rather than merging it, keeps the branch and the originating issue, logs which label or quoted instruction withheld the merge, and posts one comment on the pull request saying the ticket is **Ready** with the fix, tests, and CI result. A held run also files no follow-up issues, since unmerged work may still change under review; the items that would have been filed are listed in that same comment under `Follow-ups (not filed)`, linking equivalent open issues, for whoever merges to pick up.

## v1.2.30 - 2026-09-02

- Confirm the issue is actually closed before an agent's run counts as finished, instead of taking the agent's own exit for the work being done. An agent that timed out, stopped early, or reported success without ever merging returned exactly as one that merged its pull request did, so the run was recorded as completed, the job showed a checkmark in the UI, the project card was moved to `Done`, and the ticket it left open was never picked up again -- the watch had already marked it handled. A run that ends without an error now asks GitHub for the issue's state before it is completed: closed, and nothing changes; still open, and the work is kept alive instead of finished -- a keepalive line says so in the viewport and the same session is resumed with what is still missing (check the issue and its pull request, finish the CI, review, and merge, and do not stop until it is closed), or the agent is restarted from scratch when its session cannot be reopened. GitHub is re-read once after the closure interval before a run is treated as unfinished, so a merge it has not finished processing is not mistaken for abandoned work, and a check that fails to answer at all completes the run as before rather than trapping it in a loop.

## v1.2.29 - 2026-09-02

- Fail a GitHub read that has stopped responding instead of letting it stop the watch for good. Every read `glorp watch` makes -- a `gh` invocation, a page load or script evaluation in a browser-mode tab -- ran on the run's own context with no deadline of its own, and the poll that makes them is the same goroutine that dispatches work. A page that never finished loading, a renderer that stopped answering, or a `gh` subprocess stuck on a connection therefore parked the poll loop permanently: the agents already in flight ran to completion normally, the task counters drained to nothing, and the run then sat there alive and silent, picking up no further issues and reporting no reason, because a poll that dispatches nothing logs nothing. Each browser command and each `gh` call now carries its own two-minute deadline and fails with a line naming what timed out, so the poll reports the failure and retries on its next tick rather than never returning. A tab whose command stopped returning is also dropped and reopened on the page it was showing, since every later read of that target queued behind the command that was never coming back, and closing a tab no longer waits for a command in flight, so shutdown is not held up by one either. As a backstop for anything else that could hold the loop, a run that completes no poll for four intervals now says so once and says when polling resumes.
- Deliver the issue and comment webhooks an organization-owned Projects target's runs need, instead of leaving them to the next poll. Such a target subscribed to `projects_v2_item` and nothing else, which says only that a card moved: since the previous entry, an `issues` (edited or closed) or `issue_comment` (created or edited) delivery for a ticket an agent is already working nudges that run to check GitHub immediately rather than waiting out its tick, and a board target received none of those, so a closure, an edited description, or a new comment reached the agent a whole interval late -- a gap of minutes on a board polled slowly. The board's own `projects_v2_item` hook is untouched, and each repository currently backing the board now also carries a hook subscribed to `issues`, `issue_comment`, and `ping` and nothing more: a board target dispatches from the board, so it has no use for the pushes and pull-request activity a repository target subscribes to. Those events are a subset of the repository target's, so a repository watched both ways shares one hook and keeps its wider subscription either way round. A board whose repositories cannot be listed at that moment keeps its board hook and picks the repositories up on the next reconciliation cycle, rather than losing the subscription the whole target depends on. Watching a board therefore needs webhook access on the repositories it draws from, the same access a user-owned board has always needed.
- Relay a change made to an issue while an agent is working it into that agent's own session, instead of letting it go unheard until the run ends. A run was watched only for the one thing that stopped it -- the issue or its pull request being closed -- and that stop was terminal: the agent was killed, the work was recorded as failed, and it never learned the ticket had been closed, so the branch, the draft pull request, and the isolated clone it had opened were left behind for someone to find. An edited description and a new comment were not watched for at all, so an agent that had already read the issue kept building what the issue used to say and answered nothing anyone added to the thread; the only way through was to wait out the run and dispatch a fresh one, which threw away everything the session already knew. All three now interrupt the current prompt and resume the same session with what changed: a closure asks the agent to stop implementing and clean up after itself (close its pull request, drop the branch and the clone, and report what it removed), an edited description asks it to reread the issue and reconcile the work in progress with it, and new comments ask it to reread the conversation and treat them as part of the request. The work stays active across the interruption rather than being marked failed, and a run with no session that can be reopened keeps the old behaviour of stopping on a closure rather than being interrupted for a change it could not be told about. glorp's own handoff claims (issue #214) are never relayed, so the instances watching a ticket do not restart each other's agents on their own bookkeeping, and the cleanup run a closure starts is not interrupted again by that same closure. All three watch modes are covered: poll mode and browser mode read the change on the watcher's own tick -- browser mode reads it at all now, since its issue source reported no per-issue work state and the watcher had silently been watching nothing there -- and push mode additionally uses the `issues` and `issue_comment` deliveries it already subscribes to as a nudge to check straight away, with the change itself still read back from GitHub rather than trusted from the delivery.

## v1.2.28 - 2026-09-01

- Draw from every watched Discussions target in turn as well, instead of letting one board's backlog take every slot. The issue path was balanced in the previous entry, but discussion dispatch still walked the configured targets in order and blocked on a concurrency slot inside that loop, so `glorp watch repoA/discussions repoB/discussions` with 20 unanswered threads on repoA and 3 on repoB spent every slot on repoA -- and since discussions are dispatched ahead of issues on each poll, that backlog also delayed every issue the same poll found. A poll now collects its discussion candidates across all targets before any of them waits for a slot and interleaves them with the same rotation the issue path uses, led by whichever target has the fewest discussions already running. The two paths count their in-flight work separately, so a busy issue backlog does not lead the discussion rotation or the reverse, and which threads are eligible and the concurrency limit itself are unchanged.
- Draw from every watched target in turn when dispatching, instead of queueing one target's whole backlog ahead of another's. A poll listed the targets in the order they were configured, appended each one's issues to a single list, and the dispatch loop blocked on a concurrency slot in that same order, so `glorp watch repoA repoB` with 20 open issues in repoA and 3 in repoB spent every slot on repoA and never reached repoB until repoA drained -- and since each poll re-derives the same order, the quiet repository could be starved for the life of the run. The candidates a poll produces are now interleaved across their targets before dispatch, each target keeping its own order, and the rotation is led by whichever target has the least work already in flight, so a target that filled slots on an earlier poll yields the next ones to a target that has none. Which issues are eligible, the ownership handshake, and the concurrency limit itself are unchanged; only the order they are dispatched in is.
- Split a `gh-fix` issue that clearly describes several separable pieces of work into sub-issues, and stop treating the parent as something to implement. An issue that asks for two independently deliverable things -- "implement the fix and update the docs website" -- was picked up as one ticket and produced one pull request carrying both, so the parts could not be reviewed, merged, or reverted separately and a single agent slot held the whole thing. `gh-fix` now files each part as a real sub-issue of the original through GitHub's sub-issue API and routes it exactly as it routes a follow-up (its own kind label, the parent's still-accurate labels, milestone, assignees, project `Todo` status, and the `.glorp.json` assignment), so the next agent slot can pick one up. The split is deliberately conservative: it happens only when the issue's own words name parts that could each be implemented, tested, and merged alone, never when one part is unreachable without the other ("implement the feature and fix the related lookup bug" stays one ticket) and never on the agent's own inference, because separability usually is not determinable at the start of an issue. A parent that has been split is a tracking issue: it needs no pull request, code, or changelog entry to close, and `/gh-fix` on it only decides whether it is closeable -- closing it with a comment when every sub-issue is done, and otherwise ending the run silently rather than re-splitting it or leaving another comment, so a repeatedly dispatched tracking issue neither duplicates its sub-issues nor accumulates identical comments.

## v1.2.27 - 2026-08-31

- Close the browser-mode tabs glorp has stopped reading, instead of holding every page it ever opened until the run ends. A tab is opened per watched target and one more is shared by every conversation read, and none of them was ever closed: the issue page the handoff handshake last read stayed open long after that issue was merged, so a `-no-headless` run accumulated pages nothing was looking at and a headless one kept their renderers alive for the life of the watch. ## v1.2.4 - 2026-08-19

The main issue-list poll and per-issue dependency lookups now use the REST Search and Issues APIs (`gh api search/issues`, `gh api repos/…/issues/…`) instead of `gh issue list`/`gh issue view`, both of which query GraphQL under the hood despite looking like plain REST commands. Also slow the per-issue closure/competing-claim polling loops from every 10 seconds to every 30, matching the default base poll interval rather than tripling its request rate, since every active issue runs two of these loops in parallel and each poll costs several API requests.

- Take glorp's subprocesses down with it when glorp is killed outright. Owned subprocesses now carry a Linux parent-death signal, belong to a Windows job object that is destroyed with glorp, and on macOS and the BSDs — which have no kernel equivalent — are recorded with a small reaper process that terminates them when its pipe to glorp closes, so `kill -9` of a running `glorp watch` no longer strands the ngrok tunnel or a running agent on any supported platform.
